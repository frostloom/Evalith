# Issue #2166 回帖草稿（真实链路版）

按您的建议做了最小端到端验证，两条链路都已跑通：确定性基线（mock，可完全复现）
和真实模型全链路（DeepSeek：生成 v4-pro、被测 Agent、裁判 flash）。

## 最小闭环

```text
Evalith（外部生成）                         EvalScope（执行）
只读扫描项目源码+知识库                     导入 eval_set.v1.jsonl
→ 模型项目理解（未知项显式化）               → 调用项目暴露的 Agent HTTP API
→ 生成题目+Rubric+检查+版本                  → 多轮对话+终态检查+Rubric 裁判
→ 人工编辑/校准（版本管理）                  → 报告（task_pass/rubric_score/
→ 导出 eval_set.v1.jsonl                        evidence_coverage + 逐题证据链）
```

被测 Agent 是 ai-gateway 的真实客服 Handler，业务代码零改动，经薄 HTTP wrapper
暴露 `/v1/eval/chat`。这验证了您提出的接入方式：**用户项目只需暴露一个
HTTP API，EvalScope 负责执行与评判。**

确定性基线（10 题精选集 + mock）：9/10，rubric 0.95；无 trace 降级时
process 标准自动 `not_evaluable`、coverage 下降但照常出分。

四轮迭代的归因都由评测系统自己完成（复合题误判→裁判补全对话后转准；
退款确认题靠 SQLite 终态检查验证 confirmed=1 恰好一次）。**终态检查是
MVP 必须项**：会话层完全正常的回复与审计库真实状态可能不一致。

## 提议

1. **契约开放，生成留在外部**：eval_set.v1（题目/多轮输入/rubric/检查/执行
   配置/素材哈希/版本）作为开放契约，任何产出合格文档的工具皆可接入；
   配一页生态文档（社区快速上手：提示词包；可审计路径：独立 CLI；
   完整形态：带编辑/版本/校准的外部产品）。我们不建议把生成接口或生成
   代码放进 EvalScope。
2. **随契约进框架的**（如方向认可，细节可再讨论）：契约校验器（导入即拒错
   文档，可独立进 CI）、agent_api 适配器（health/chat/reset 约定 + session
   关联）、只读终态检查执行器（SQLite ro/路径拒绝/loopback，代码强制）、
   报告字段与降级语义（task_pass/rubric_score/evidence_coverage）。
3. **执行走用户项目暴露的 Agent HTTP API**，业务代码零改动。
4. **MVP 评判 = 最终回答 + Rubric + 业务终态检查**；多轮任务把完整对话喂给
   裁判（成本近零）。**trace 后续分层引入**（OTel 最短路径 → 消费已有审计
   表/日志 → 网关观测点），session 关联头先约定。

## 想一起确认的问题

- 契约自身的版本治理：schema 演进与弃用归谁、如何迁移；
- 与 EvalScope 现有任务/数据格式的兼容或迁移口径；
- 题目文本是源码衍生品（必然复述业务规则），契约级安全字段我们起草了
  data_classification / redaction 声明 / judge_input_whitelist / 报告分享级别
  一组要求（见附 PRD），是否随契约一并考虑；
- 环境契约（fixture 金额/播种数据/话术假设）做声明字段 + 校验器比对 +
  单题 dry-run 的可行性——demo 四轮里它决定"当天能否闭环"。

## 实践中踩到的坑（供契约设计参考）

- 生成侧 fixture 与执行侧环境的状态契约需对齐，人工编辑环节应保留在流程里；
- 终态断言要用会话内不变量（如"本会话 confirmed=1 的退款数=0"），
  避免共享环境状态被其他任务污染；
- Judge 需要显式配置，JUDGE_ONLY 下无规则回退；状态型任务需要 batch=1 与
  环境 reset，框架缺通用复位接口。
