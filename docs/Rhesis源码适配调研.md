## 许可和部署约束

仓库根 `LICENSE` 将除 `/ee/` 外的源码列为 MIT Expat，复制或分发时需保留版权和许可声明；`ee/` 适用其单独许可，第三方内容按 `NOTICE` 和各自许可核对。**根许可证明确说明其标识、商标及列出的品牌素材不属于 MIT，未经书面许可不得使用**，做 Evalith 品牌时须移除或替换相关素材并检查其他权利。

`docker-compose.yml` 包含 PostgreSQL、Redis、backend、worker、beat、frontend 等服务，比轻量单进程方案更重；尚未系统测量资源和启动成本。本地体验时关闭遥测并将前后端限制为本机监听；实际部署前仍需检查版本、配置及数据去向。体验中修正了本地健康检查配置，用户模型配置和数据库保留，服务已停止。

## 建议的验证顺序

1. 固定上游提交与依赖，检查可用许可范围；在独立环境启动未修改版本，验证模型配置、项目/会话、题集生成、逐题持久化与结果展示。记录本地资源、模型调用与数据出站。此步骤需要具体运行配置，但不需要预设任何真实业务项目为产品基准。
2. 设计一个不代表特定业务的最小合成验证：本地项目资料读取、任务包含文件或状态变化、独立检查和故障清理；验证新增适配层能否在 Rhesis 会话和执行路径中闭环。合成样例仅证明技术能力，不定义产品覆盖范围。
3. 比较直接修改 Rhesis 与将其作为独立服务集成：统计必须修改的数据模型、界面、agent 工具、执行路径和升级冲突。重点核实本地项目权限、非对话任务、环境创建、预算和历史快照。
4. 如核心抽象可扩展且维护成本可接受，再选择源码 fork 策略并制定实现计划；否则保留可复用模块或通过 API 集成。重大设计仍以通用 PRD 为准。

## 主要不确定项

这是静态抽样，不是全面代码审计；未验证实际 UI、实时事件、现有选择范围、现有版本保存与安全隔离。评估时应使用冻结提交而非假设在线文档与该提交完全一致。当前嵌套仓库仅本地克隆，没有创建远程 fork、提交源码或将其纳入 Evalith 的版本管理。
