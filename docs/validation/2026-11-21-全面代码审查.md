## 4. 安全维度发现

审查文件：`security.py`、`project_access.py`、`source_copy.py`、`config.py`、`verification.py`，交叉对照 `execution_process.py`、`api.py`、`db.py`。

### 【高】S1. 沙箱证据回收按路径读取输出文件，符号链接可越权读出任意用户可读文件（已实测）

- 位置：`execution_process.py:129-133`（以 `wb` 打开 `stdout.txt`/`stderr.txt`）与 `:191-193`（进程结束后 `read_text()` 按**路径**读取，此时父进程持有的 fd 已随 `with` 块关闭）。
- 场景：被测 Agent 在沙箱内把自己可写的 case 目录里的 `stdout.txt` 换成指向 `/Users/me/.ssh/id_ed25519` 的符号链接。沙箱 profile 的 `deny file-read*` 拦截它自己读，但 Evalith 结束后以**完整用户权限**沿符号链接读出，内容进入 `observation["stdout"]`——(a) 存库并返回 UI（仅脱敏已保存的密钥字面量）；(b) 最多 40KB 作为判分证据发送到外部模型服务商。同时击穿沙箱读拒绝与 README“路径越界与符号链接逃逸被拒绝”的承诺。
- 实测：沙箱内直接读目标文件被拦截（BLOCKED）；经 `stdout.txt` 符号链接被 Evalith 读出，标记串完整出现在结果里。
- 测试缺口：沙箱测试只用行为良好的程序验证读写拒绝，无对抗性输出文件测试。
- 修复方向：从仍打开的 fd 读取（`with` 块内 read/seek），或结束后以 `O_NOFOLLOW` 打开并校验 `(dev,ino)` 与启动时一致。

### 【中偏高】S2. sandbox-exec profile 使用 `(allow default)`，mach IPC 完全未限制（已实测）

- 位置：`execution_process.py:49-56`。只 deny `file-write*`/`file-read*`/`network*`，mach-lookup、process-info 等默认放行。
- 场景：被测 Agent 可与任意 launchd 服务做 Mach IPC，绕过文件读黑名单。实测 `defaults read` 经 cfprefd 成功返回；同类路径下最敏感的是 SecurityServer——`/usr/bin/security` 在可执行白名单内，登录钥匙串中未被 ACL 拦截的条目可被同用户沙箱进程经 IPC 读取。
- 修复方向：显式 `(deny mach-lookup)`（按需放行必需服务）、`(deny process-info*)`，收窄默认放行面。

### 【中】S3. loopback 网络放行为 `localhost:*`——任意本地端口，而非仅模型桥端口（已实测）

- 位置：`execution_process.py:98-101`。
- 场景：Go 适配器下被测 Agent 可探测/访问本机所有回环服务（开发服务器、本地数据库、其他 Evalith 实例、绑定在 127.0.0.1 的 Docker API 等），而设计意图只是访问模型桥。实测 `loopback=True` 时连接请求到达网络栈未被拦截。
- 修复方向：收窄为 `(remote ip "127.0.0.1:<bridge_port>")`。

### 【中】S4. 口令派生密钥使用无盐单次 SHA-256

- 位置：`security.py:1605-1616`。`EVALITH_SECRET_KEY` 非 Fernet key 时单次哈希直接作密钥。
- 场景：用户设置人类口令；攻击者拿到 `evalith.db` 备份即可 GPU 离线爆破（无盐、无迭代、跨安装可预计算），与“密钥加密保存”的强度承诺不符。
- 修复方向：scrypt/PBKDF2 + 每安装随机盐（盐可与密文同存）。

### 【中·条件性】S5. `EVALITH_ALLOW_REMOTE=1` 打开后完全没有认证层

- 位置：`api.py:80-121`、`config.py:30-32`。
- 场景：remote 模式下网络内任意主机可创建项目导入任意可读目录、触发本地命令执行、把扫描内容发往任意 HTTPS 主机，S1 的外泄也可被远程触发。文档只写"trusted network"。
- 修复方向：remote 模式强制访问令牌，或 README 明确列为已知限制。

### 【低】

- **S6** `security.py:1617-1625`：secret.key 权限被外部改宽不修复；空/损坏文件报错难排查；无密钥轮换机制。
- **S7** `db.py:117-127`：`EVALITH_DB_PATH` 指到其他目录时，含密文密钥的数据库以默认 umask（常为 0644）创建；建议创建后 chmod 0600。
- **S8** `project_access.py:210-217`：敏感排除对祖先目录名匹配会整项目误杀（fail-closed 方向，可用性问题）；`.env~`、`.bash_history` 等变体未覆盖（`.ENV` 大小写已正确覆盖）。
- **S9** `verification.py:27-38`：evidence_path 校验与使用间的理论 TOCTOU；当前时序不可利用，仅记录。
- **信息**：`mask_secret` 泄露末 4 字符（当前无调用点，死代码）；`go build` 非沙箱编译不可信源码属已声明限制；`model_gateway` 全部 httpx 调用 `trust_env=False` 且 key 仅进 Authorization 头——正确。

## 5. 模型网关与评测域发现

审查文件：`model_gateway.py`、`grading_plan.py`、`evaluation_calibration.py`、`evaluation_assets.py`、`evaluation_store.py`、`evaluation_library.py`、`evaluation_preparation.py`、`result_analysis.py`、`executor_configs.py`。

### 【高】D1. 模型调用完全没有重试/退避；一次瞬时失败把已消耗的执行永久变成不可评分

- 位置：`model_gateway.py:361-374`（单次 `httpx.post`，429/5xx/网络抖动一律立即抛错，已复核确认全文件无 retry/backoff）；`evaluation_runner.py:1059-1071`（judge 失败 → 永久 `review_required`）。
- 场景：run 执行到第 N 题，目标 Agent 已在沙箱跑完（成本已花），判分时上游一次 429 → 该题永久不可评分、score=None。没有“只补判分不重跑目标”的路由；校准同理（第 15 个样本瞬时失败 → 整个 job failed，前 14 次调用花费无部分报告保留）。失败调用还照常消耗 `max_model_calls` 预算（`reserve_call` 先占额、失败不退还）——瞬态故障可烧光全部预算且零产出。无客户端限流，多 run 并行更易触发 429，与不可恢复复合。
- 测试缺口：所有模型交互测试 monkeypatch `complete_json`，HTTP 层从未被 429/超时打桩。
- 修复方向：幂等请求加有界重试（429/5xx/连接错误，指数退避）+ 提供 re-judge 端点只补判分 + 失败调用退还预算（或单独记账）。

### 【高】D2. Grader 只有版本计数、没有版本内容：校准历史在编辑后不可审计

- 位置：`evaluation_library.py:115-131`（编辑原地覆盖，仅 `version+1`）；`evaluation_store.py:86-99`（无历史表）。对比题目有专门的 `evaluation_task_versions` 不可变版本行。
- 场景：校准报告记录 `grader_version: 3`，但 version 3 的 rubric/check/threshold 内容在任何后续编辑后永远丢失——无法回答“这份一致率 100% 的校准当时用的判定标准是什么”。run 历史本身安全（grader 全量快照冻结进 run 记录），但 grader 级谱系不可回溯。附带：归档 grader 无任何只读路径（list 也过滤掉），归档即不可见。
- 修复方向：为 grader/test_set 建与 task 对称的版本表；归档记录保留只读访问。

### 【中】

- **D3** 校准无样本量/类别门槛：1 个样本即可标 `calibrated`；全部 `missing_evidence` 样本时退化 judge 也能“全对”。报告只有 total/matched，无样本量、混合度、过拟合提示（`evaluation_calibration.py:37,200-212`）。
- **D4** target/judge 模型在 plan 阶段不校验存在性与 stub：结构上无法评分的 run 可以正常启动，目标真执行完后判分才失败，把失败推迟到最贵的时刻（`evaluation_runner.py:171-201`；对比模拟器有完整同步校验）。
- **D5** `gateway.cancel_check` 是死代码：取消不打断进行中的模型 HTTP 请求，阻塞至超时且照常计费（`evaluation_runner.py:428` 赋值后全仓库无读取点，已复核确认）。
- **D6** `assets.generate` 持久化非原子：generation 记录先标 completed 再逐条分事务落盘，中途失败留下“completed 的残缺 generation”（`evaluation_assets.py:177-179`；对照 preparation 已用 `create_bundle` 单事务并有测试）。
- **D7** `store.list` 每 kind 硬上限 200、无分页：长期使用后最老的 run/校准/分析从列表静默消失（按 id 仍可取但 UI 无入口），与“历史不被改写”的精神相悖（`evaluation_store.py:83`）。
- **D8** PUT grader 不带 `model_config_id` 时静默清除判分模型绑定，下次 run 静默回退项目级模型，判分口径变了无任何提示（`evaluation_library.py:85-125`；与 task_kinds 的保留策略不一致）。

### 【低】

### 【高】R1. 宽松 JSON 解析/序列化把 `NaN`/`Infinity` 写入 run 记录，毒化整条记录（已复核确认）

- 位置：`evaluation_runner.py:649-653`（`json.loads(stdout)` 默认解析器接受 `NaN`/`Infinity` 字面量）+ `evaluation_store.py:95`（`mutate` 的 `json.dumps` 未传 `allow_nan=False`）。对照 `create_bundle`（`evaluation_store.py:60-61`）有 `allow_nan=False`——主写入路径漏了。
- 场景：被测程序输出 `json.dumps({"score": float("nan")})` 这类常见 Python 数值代码 → nan 进入 observation → 裸 `NaN` 写回数据库。之后任何严格 JSON 解析器（前端 `JSON.parse`、`jq`、导出脚本）解析该 run 的 detail/list 响应整体失败——**一道题的 stdout 让整个批次在 UI 里不可读**。judge 分数路径已有 NaN 防护（范围比较天然拒绝 nan），observation 路径没有。
- 修复方向：解析用 `parse_constant` 拒绝、序列化统一 `allow_nan=False`；修复成本极低，性价比全表最高。

### 【高】R2. 每题 observation 全量内嵌 run 记录 + 全量重写 + 20Hz 全量解码：声明上限内的可扩展性缺陷

- 位置：`evaluation_runner.py:872-881`（`_save_result` 每次把含全部历史 observations 的整条记录重写）；`:329-333`（`cancelled()` 每次 `store.get` 全量解码整条记录）+ `execution_process.py:145-158`（poll 每 50ms 调一次 cancel → 每秒 20 次全量解码）；每次模型调用经 `reserve_call`+`_finish_call` 再各重写两次；`evaluation_api.py:133-138`（列表一次性返回 200 条全量记录，与 F1 同根）。
- 场景：单题 stdout 上限 200 万字符、stderr 20 万。60 题的 run 可长成几十至上百 MB 的单条记录：取消轮询每秒 20 次全量解码该 blob、每次模型调用 2 次全量重写、SQLite 写放大随题数二次增长。在产品自己声明的上限内即可让运行明显变慢、DB 膨胀、列表接口超时。
- 修复方向：observation 拆行存储（或至少 cancel 检查走轻量状态列）；与 F1 的列表瘦身一并设计。

### 【中】

- **R3** 后台线程缺顶层兜底，尾部 DB 写在 try 之外：最后一题的结果落盘与终态 `store.update` 都在 per-task try 外，任一尾部写失败（sqlite busy 超时、磁盘满）→ 线程静默死亡，run 永久卡 `running`，进程内无看门狗，只能靠重启恢复（`evaluation_runner.py:1093-1126`；`result_analysis.py:138`、`evaluation_api.py:295-299` 同型）。
- **R4** cancel 与最终状态写入的竞态 + 双实例共库时 `interrupted` 可被“复活”为 `completed`：最终 `store.update(status=terminal)` 无条件覆盖不检查 `cancelling`；启动恢复只认状态字符串无属主存活检测（PID/心跳），两个服务实例共享 `EVALITH_DB_PATH` 时出现非法状态转移（`evaluation_runner.py:335-341,1118-1126`）。
- **R5** Harbor 清理语义两处缺口：killpg 杀的是 harbor CLI 进程组，真正跑被测目标的容器由 Docker 托管会继续跑到自身超时，而 cleanup_status 报 `completed`——“清理失败可区分”对容器层不可见；且 CLI 看门狗（300s+3×timeout）可短于自己声明的 `build_timeout_sec=900`，首次拉镜像+构建会被误杀并误分类为执行失败（`evaluation_runner.py:757-789`）。
- **R6** 桥接请求体无大小限制，而调用方是沙箱内的被测进程：bearer token 本来就交给被测 Agent，有缺陷的目标可向桥 POST 数百 MB 在解析阶段耗尽内存，预算检查发生在 body 已读入之后（`evaluation_api.py:188-208`）。附带：非 ASCII Authorization 头会因 `compare_digest(str,str)` 抛 TypeError → 500。
- **R7** `budget_usd` 的实际语义是“禁用一切模型调用”，且 preview/start 不告知：用户带 `budget_usd=10, max_model_calls=8` 启动，第一个评分调用即 BudgetStop、整批 unscored。诚实但应在该参数可用时明确警告，目前是个陷阱（`evaluation_runner.py:353-354`）。README“每次模型请求前检查调用上限”声明属实——`reserve_call` 在 `BEGIN IMMEDIATE` 内原子检查+占位，Go 适配器并发也不会超支。

### 【低】

- **R8** `run_list`/`environment_list` 不校验项目存在：未知 project_id 返回 200+空列表，与 tasks/jobs 路由的 404 行为不一致（`evaluation_api.py:106,135`）。
- **R9** `bounded_process` 末尾无条件 killpg 的 PID 复用窗口（leader 已 reap 后按旧 pgid 发 SIGKILL，理论上可误杀复用该 PID 的无关进程组；概率极低但后果严重）；输出上限 4MB 是 50ms 轮询近似，两次 poll 之间可写任意量（读回有 2MB 截断兜底）（`execution_process.py:152-190`）。
- **R10** 模块导入副作用 + 默认数据目录是 CWD 相对路径：`import evalith.api` 即建库跑恢复；`python -c` 或测试收集会在 CWD 创建 `.evalith/`；不同目录启动得到不同 DB（`api.py:291`、`config.py:17-18`）。建议默认 `$HOME` 下或要求显式配置。
- **R11** GET 带副作用：`get_project_detail` 每次都重扫描源目录并可翻转理解状态，非幂等且每次全盘扫描（`service.py:591,1075-1106`）。
- **R12** N+1：`serialize_project` 对每个项目再查并解析完整 manifest；`versions()` 逐版本单独查询；`list_messages` 全量载入会话（`service.py:617-635` 等）。
- **R13** schema 无版本管理：按列名字符串匹配的 ad-hoc `ALTER TABLE`，无 `PRAGMA user_version`/迁移框架，演进易漂移（`db.py:129-141`）。连接管理本身正确（每操作新连接、WAL、busy_timeout、`BEGIN IMMEDIATE` 原子读改写）。
- **R14** 输入校验不一致：消息有 8000 字上限但项目名与 supplemental 内容无长度上限；`create_model_config` 用 `except Exception`+字符串匹配判 UNIQUE 冲突（`service.py:260-265,370-374`）。
- **R15** 失败的环境准备留下孤儿目录（`exist_ok=False` 创建后状态 failed 无法重用）；`runs/` 每题整份 copytree 与 harbor 产物永久保留属设计意图，但失败环境目录是纯泄漏且无总量控制入口（`environments.py:285`）。
- **R16**（存疑）LocalHostMiddleware 客户端白名单可能不含 IPv4-mapped `::ffff:127.0.0.1` 形式，某些双栈配置下本地请求被 403；未实测验证，列为存疑（`api.py:80-97`）。

## 8. 工程卫生与仓库发现（独立检查）

- **【高·非代码】公开仓库无根许可证**：`github.com/frostloom/Evalith` 为 PUBLIC，无 LICENSE。默认“保留所有权利”——使用者无合法使用授权，贡献者无授权依据。阶段 5 报告 §8.3 已自行标记“需维护者决定”，至今未收口。**这是当前最便宜也最优先的收尾动作。**
- **【中】`rhesis/` 142MB 参考检出未跟踪也未忽略**：`git status` 长期脏；根目录 `.pytest_cache/v/cache/lastfailed` 显示曾发生过一次从仓库根误收集 `rhesis/` 的 pytest 运行（开发账本亦有记录）。建议加入 `.gitignore`（或移出仓库并在 docs 记录路径）。
- **【低】CI 触发配置**：`on: push`（无分支过滤）+ `pull_request` 使同一代码在 PR 流水线跑两遍；可改 `on: push: branches: [main]` + `pull_request`。
- **【低】`start-local.sh:35`**：`node_modules` 存在即跳过安装，`package.json` 变更后重启不会更新依赖；可在存在 `package-lock.json` 比 node_modules 新时重跑 `npm ci`（或文档提示）。
- **【低】`workbench/`、`stage0/` 为阶段 0 归档脚手架**（含 EE-free 构建器与固定 pin），已无产品路径引用；保留可作历史依据，但建议在目录 README 顶部加“已归档，不参与当前产品构建”声明，避免新读者误以为活动代码。
- 合规做得对的地方：前端 `RHESIS-LICENSE`（MIT 归因）与 `NOTICE.md`、字体 OFL 文本均在位；`examples/` 中的“密钥”是显式标注的合成假密钥，无真实泄漏。

## 11. 做得好的方面（平衡记录）

- **运行快照冻结链完整且被测试钉死**：版本行 + grader 快照 + 编译后 checks + 环境/模型指纹 + plan_digest 复核，后续编辑不改写历史（多项专项测试）。
- **诚实的失败语义**：判分失败绝不伪装成低分（review_required/score=None）；HTTP 错误不能通过否定检查；执行错误、预算停止、取消、中断、清理失败状态分明且有测试。
- **金额语义**：`cost_usd` 严格 None（未知不计零）、非 None 预算 refuse-to-start，贯穿 runner/分析/环境三层。
- **密钥处理面干净**：Fernet（认证式加密）、序列化白名单永不返回密钥、`trust_env=False`、仅进 Authorization 头、双重脱敏（含 URL 编码变体）、日志 RedactionFilter 挂 root + uvicorn、bridge token 加密存储常量时间比较。
- **扫描侧路径安全扎实**：dir_fd 相对打开 + 每组件 `O_NOFOLLOW`、(dev,ino) 锚定、硬链接/FIFO 拒绝、敏感排除不可被用户选择覆盖且 casefold 适配 macOS（67 项路径安全 + 60 项脱敏测试）。
- **前端竞态防护与 XSS 面**：四重竞态守卫 + StrictMode/迟到响应测试；Markdown 渲染 `skipHtml` + 协议白名单 + `noopener noreferrer`，有显式 XSS 回归测试；轮询清理、列表 key、防重复提交、IME 处理、键盘导航、焦点还原等均有测试。
- **SQLite 使用规范**：每操作新连接、WAL、busy_timeout、读改写 `BEGIN IMMEDIATE`；data 无法伪造 id/status。
- **启动恢复完整**：覆盖 running/pending/preparing/cancelling × run/job/environment/analysis，run 内逐题结果转 interrupted 并保留证据，清理置 `unknown_after_restart` 而非谎称完成（`evaluation_api.py:57-102`，有测试验证不重复打断已完成 run）。
- **进程所有权与清理可见性**：`start_new_session` 独立进程组、SIGTERM→SIGKILL 升级、兜底清理孙进程、清理失败作为一等状态上报且不与低分混淆；最近的 `a45789a` 修复了“强制 SIGKILL 成功被误报为清理失败”并有 RED→GREEN 回归。
- **无 shell=True**；harbor 脚本插值全部 shlex.quote/base64；环境变量白名单（无 HOME）。
- **预算原子性**：`reserve_call` 在 `BEGIN IMMEDIATE` 事务内“检查+占位”后才发现请求，Go 适配器并发打桥也不会超调用上限；README 对应声明经独立复核属实。

**测试盲区共性**（四份审查一致指出）：现有测试对“声明语义”（预算停止、清理失败、重启恢复、证据不足、快照冻结）覆盖扎实，但对**时序与故障注入**几乎为零——无并发 cancel、无模型调用在途取消、无 DB 故障下的线程存活断言、无 NaN/超大 body/对抗性沙箱输出等恶意输入、无真实 Harbor 耗时路径、无大规模负载。建议优先补一个“store.mutate 可注入失败”的测试钩子，上述多数中高危都能以它为基础设施稳定复现。
