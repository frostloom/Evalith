# Evalith：业务 Agent 评测工作台初步方案

状态：讨论稿｜2026-11-04

本文记录产品方向和待验证的技术方案，不代表实现承诺或已经完成的能力。

## 1. 要解决的问题

AI Gateway、Myink 等业务 Agent 有项目特有的流程、数据和成功条件。通用 benchmark 可以衡量部分通用能力，却不能直接回答“退款是否正确、安全”或“修改后的故事是否遵守已有设定”。人工整理题目、环境和评分规则又需要理解大量分散的项目资料。

Evalith 是一个可视化工作台：分析项目代码、文档、已有测试和评测资产，辅助设计有证据来源的项目专属评测题集；用户浏览并确认规则后，在隔离环境中运行评测，查看结果和证据。优先探索复用 LangChain Eval Engineering Skill 的方法及 Harbor 的执行能力，而不是从零重建所有环节。

## 2. 目标与范围

首期目标是验证一条完整链路：选择本地项目，分析一个业务流程，生成少量候选场景及评分规则，准备隔离环境，在工作台发起运行，并展示可追溯结果。首个候选样板为 AI Gateway 的退款流程；随后用 Myink 的写作或审核流程检验复用性。

主要面向开发者和了解业务的项目负责人。任务级业务场景是重点，组件级测试作为诊断补充。题集可用于回归，以及在相同条件下比较不同模型或 Agent 版本。

首期不承诺任意项目一键接入、不修改被测项目的业务规则、不连接生产数据或执行真实退款，也不把自动生成的题目当成已验证的业务真值。通用 benchmark 和通用编程 Agent 评测可以作为后续扩展，不是首期核心。

## 3. 用户流程

1. **选择项目与范围**：选择本地目录和要评测的 Agent、业务流程；展示将被分析的资料范围。
2. **分析项目**：识别入口、Agent、工具、业务规则、依赖、已有测试和评测；提供可核对的文件位置与版本。
3. **确认评测方向**：展示候选业务场景、已有覆盖和待澄清问题，用户选择要生成的题集。
4. **设计题目**：生成初始状态、任务、多轮交互、预期行为、判定标准、证据来源和候选验证方式，覆盖正常、边界、异常及相关安全场景。
5. **浏览和确认**：区分当前行为基线、由需求支持的业务验收候选以及证据不足或冲突项；允许编辑、接受或暂缓。高风险规则的最终确认策略尚待确定。
6. **准备并校验环境**：生成项目接入配置、测试数据和验证器候选；检查隔离、依赖、数据重置及可观测性。
7. **运行与查看**：用户选择版本、模型和题集后启动评测；查看每题状态、对话和轨迹、验证证据、失败原因、耗时与已知用量。
8. **维护与回归**：保存题集、规则、环境及运行版本；修改后可比较结果，明确版本或配置差异。

## 4. 规则依据与判定原则

- **需求与业务文档**说明期望，可能过时或不完整；**代码和配置**反映实现，可能包含缺陷；**测试和历史评测**反映已有约束和覆盖，也可能有遗漏。保留来源，不假设任何一方永远正确。
- 根据代码推导的现状题标记为“当前行为基线”，不自动称为业务正确。文档、代码和测试冲突时展示双方依据；对潜在问题给出待确认项，不擅自改写现状或替用户决定业务意图。
- 对静态分析不能证明的行为标记为待运行验证或证据不足；代码路径、运行结果和用户确认各自留痕。先自动生成候选，再集中展示重要不确定项，以控制人工成本。
- 结果优先：核验最终业务状态；过程重点检查必要步骤和禁止行为，不强制唯一的工具顺序。硬性约束违反时不能被其他质量分抵消。
- 可确定验证的事实优先使用独立的代码或状态检查；语义质量可使用模型或人工复核，并保留原文证据、评分依据和争议。缺证据不判通过。

## 5. 题目与评分数据

一条题目至少应包含：唯一 ID 和版本、业务目标、来源及可信状态、初始数据和依赖、用户输入与多轮计划、适用约束、预期结果、证据要求、判定方式、清理或重置要求，以及待确认事项。评分规则与题目关联，但应能独立版本化。

示例：退款尚未确认。隔离环境中准备账户、订单和余额；发送退款请求；检查回复及相关操作；由验证器独立核对退款记录和账本。是否必须确认应以项目中明确的业务依据或用户确认为准，不能凭示例假定实际项目已有该规则。

每条检查分别标注 `确定性状态检查`、`轨迹检查`、`模型语义评分` 或 `人工复核`，以及所需证据。仅有自然语言题目不等于可自动执行。

建议展示的就绪状态：

1. **候选**：已生成场景或规则，尚待确认。
2. **设计完成**：题目、判定和来源已整理，执行依赖仍未全部验证。
3. **可运行**：环境、Agent 接入和证据采集已验证。
4. **已校准**：验证器用已知正确、错误及边界样本检查过；不意味着所有业务意图均已证明。

## 6. 隔离执行设计

每次运行创建独立测试环境，包含被测 Agent 版本、独立测试数据库、必要缓存、执行器和验证器；外部支付、短信等副作用服务默认使用可控替身或明确指定的测试接口。以项目实际依赖为准，不假设所有项目都需要相同服务。

**项目环境模板**描述构建与启动方式、迁移、健康检查、Agent 接口、状态读取和清理；**题目数据**描述特定案例的初始状态和期望。题目之间使用独立环境或经验证的重置机制；并发执行不能共享可变业务数据。

默认不依赖本机生产数据库、用户会话或真实业务凭证。生成的容器配置需要检查挂载、网络、密钥及外部写入；Docker 本身不是对任意不可信代码的完整安全边界。日志应避免保存凭证和真实敏感数据。运行结束保留必要证据与配置指纹，按明确的保留策略清理容器、测试数据及临时资源。

模型既可以是真实接口，也可以是固定响应的替身。前者衡量完整 Agent 但有费用和波动；后者用于流程与基础设施测试，不能宣称真实模型能力。**默认采用哪一种尚未决定**；每次运行必须记录模型、替身、版本、网络依赖和资源限制。

## 7. 系统组成与复用候选

```text
可视化工作台：项目 / 题集 / 确认 / 运行 / 结果
       ↓
项目分析与评测设计：项目事实、来源、候选题目、规则与版本
       ↓
项目接入与任务编译：环境模板、数据、Agent 适配器、验证器
       ↓
执行适配层 → Harbor 等候选执行器 → 隔离环境与证据
```

- **LangChain Eval Engineering Skill**：参考其仓库发现、任务规格、环境、验证器与校准流程；验证能否作为工作台的 Agent 能力复用。其流程需要用户审核，不假定能无人值守生成可靠题集。[Skill](https://github.com/langchain-ai/langchain-skills/blob/main/config/skills/eval-engineering/SKILL.md)
- **Harbor**：优先验证其任务格式、容器环境、Agent 适配与 verifier 能否支持业务 Agent 的服务、数据库和多轮交互。使用前检查项目实际安装版本，不能假设最新文档能力在旧版中存在。[任务文档](https://docs.harborframework.com/tasks/overview)
- **其他候选**：DeepEval 的文档生成和多轮数据、Promptfoo 的安全测试、现有项目测试及评测脚本可按实际需要评估；不预先承诺集成。

Skill 仓库公开采用 MIT 许可证；若复制或分发其内容，保留相关版权与许可声明。其他引入组件分别检查许可和依赖。

## 8. 运行结果与证据

结果至少区分：**通过、任务失败、环境或执行失败、验证失败／待复核、未运行**。保存失败和超时，不以重试后的成功覆盖原始记录。报告展示计划数、实际运行数和各类状态，明确分母；未知用量或成本不记为零。

每次运行记录题集、规则、被测代码、环境及配置版本，保留用户输入、可公开的 Agent 回复和工具轨迹、验证器检查及状态快照。模型评分需记录模型与依据；比较版本时说明环境、模型和数据是否一致。敏感数据处理与保留期限需要后续细化。

## 9. 首个验证样板

以 AI Gateway 退款流程为候选，先做 1–2 个场景：在隔离容器中运行真实业务代码和测试数据库，建立模拟账户与订单，执行对话，独立核对账本或退款状态，展示题目来源和运行证据。是否使用真实模型、依赖模拟范围和具体场景，以准备阶段实际条件和用户选择为准。

验证标准：能重复建立和清理隔离环境；正确区分任务失败、环境失败与无法验证；至少一个 verifier 能在已知正确及错误状态下给出预期结果；工作台能展示来源、配置和证据。不以少量题目通过宣称业务整体可靠。

随后以 Myink 的一条审核或反馈修订流程验证迁移，重点观察数据初始化、文本证据、语义判定和最终状态与退款场景的差异。

## 10. 待讨论与待验证

1. 真实模型与固定响应模型的默认策略、费用和使用限制。
2. 高风险规则何时需要人工确认；其他候选题如何批量审核。
3. 工作台形态、技术栈、执行服务部署方式和项目接入边界。
4. Harbor 与实际业务 Agent、多轮交互和现有本地版本的兼容性。
5. 如何校准模型评分、版本化证据，并限制输出或数据泄露。
6. 项目环境自动发现可做到什么程度，何时需要开发者补充配置。
7. 题集及运行数据的存储、清理、共享和访问控制。
