# Evalith 通用评测架构调研

状态：调研与建议，非实施承诺｜2026-11-04

## 结论

Evalith 的核心应是跨项目的评测资产与运行管理，不以对话作为必需形式，也不将 Harbor 的任务格式作为唯一真源。先设计小而明确的任务、项目接入、证据和结果契约；以 Harbor 为首个执行后端候选，以 Inspect 为对照，使用 Gateway 和 Myink 的实际路径做同条件技术验证后再选型。LangChain Eval Engineering Skill 用于参考发现、设计、审核、验证和校准流程，其当前工作流直接面向 Harbor，不能假设它天然后端无关。

以下为文档调研和本地项目 README 的初步发现，尚未安装、运行或验证任何框架或项目，也未确认当前安装版本与在线文档一致。

## 不同项目对抽象的要求

- [AI Gateway README](../../ai-gateway/README.md) 描述了客服服务、租户隔离、写操作确认、充值/订阅等业务，且已有 `eval/cases` 评测资产。应盘点全部客服场景和现有用例，区分已有覆盖与缺口；不能只检验回复，还要核对实际状态和禁止的副作用。
- [Myink README](../../Myink/README.md) 描述了规划、生成、审核路由和记忆等工作流；审核可路由到 pass、rewrite、replan 或人工复核。这里的输入和证据包括作品设定、文本、任务状态、审核依据和持久化结果，不必是对话。上述均为项目文档描述，具体接入点及可执行性待查证。

## 建议的最小契约

1. **项目接入**：版本、启动及健康检查、输入接口（API、CLI、事件或文件等）、状态读取和清理；列出依赖与能力，不假设项目使用某种 Agent 框架。
2. **任务规格**：版本、来源与确认状态、初始环境和数据、可见输入或事件序列、约束、成功及禁止条件、证据要求、验证器和资源限制。对话只是可选交互类型；隐藏答案和验证器不能泄露给被测 Agent。
3. **执行后端**：声明支持的能力，准备环境、提交任务、获取状态和证据、取消及清理。无法表达的需求应明确报不支持，不静默降级；不同后端可保留原生配置和结果。
4. **验证与证据**：独立采集最终状态、文件、事件或轨迹；每项检查记录方法、证据、结论与错误。确定性检查优先，语义判断或人工复核按需使用；硬约束不能由平均分抵消。
5. **运行记录**：记录任务、规则、代码、环境、模型、适配器及验证器版本；保留原始运行和失败、超时、不可验证的状态，未知成本不记为零。重试作为新尝试记录。

契约先用两个项目的真实样例检验，再决定是否形成更完整的插件协议；暂不预先实现所有后端或设计庞大的通用配置格式。

## 对比验证计划

1. 只读盘点 Gateway 客服入口、工具、现有评测、测试环境和重置路径，建立带来源的全场景清单与覆盖矩阵。选一个涉及状态变化或确认的代表场景；具体规则以证据为准。
2. 只读盘点 Myink 一条审核或修订任务的触发、异步状态、产物和读取方式，选择一个非对话样例。确认所需隔离依赖与模型替身可用性。
3. 固定同一任务、被测版本、数据、验证规则和资源限制，分别尝试 Harbor、Inspect，以及必要时的 Compose 薄执行器。先用固定响应或已知输出验证基础设施，再在明确模型和费用的条件下评估真实 Agent。
4. 每个候选记录接入代码量及改造点、启动/清理可靠性、并发隔离、异步和多轮支持、状态/轨迹证据、隐藏验证材料、失败分类、重试、成本与许可。通过正确、错误、边界和缺失证据样本检验 verifier。
5. 以两类任务均可重复运行并正确区分业务失败、基础设施失败和无法验证为选择依据；记录不支持的能力和项目特定代码，必要时保留多个后端。Gateway 的完整客服场景覆盖在底座验证后继续按矩阵推进。

## 主要未决问题

- 两个项目实际入口与隔离数据准备能否被框架驱动，需实测；文档所述能力不等于可直接接入。
- 任务格式与现有 Gateway 评测资产如何映射，能否复用现有验证器而不复制其错误。
- 异步运行、人工确认、跨服务状态、持久化证据和清理如何映射到各后端；高风险规则审核及真实模型预算如何设置。
- 环境和业务数据的安全边界、出网策略、数据保留及多用户权限。容器本身不构成对不可信代码的完整安全边界。
