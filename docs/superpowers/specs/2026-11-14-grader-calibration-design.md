# Grader calibration against known-outcome samples

User direction (2026-11-14): continue with the next capability. Chosen: grader calibration — the PRD's task-preparation states name 验证方式已校准, `calibration_state` is written as `unverified` on every standard and task, and nothing ever calibrates or consumes it. Harbor execution and adaptive multi-turn remain unimplemented and are not claimed by this change.

Calibration verifies a reusable judge grader before it is trusted. The user supplies a small set of known-outcome samples (name, observed document, expected verdict in {pass, fail, missing_evidence} — the known correct / wrong / boundary / missing-evidence cases the stage-3 acceptance asks for). A calibration job compiles the grader exactly as a real run does — same `grader_check` criteria compilation, the same judge system prompt (extracted to one shared constant), the same verbatim-evidence validation, threshold and missing_evidence semantics — and sends one model request per sample using the grader's model or an explicit supported override. Per-sample expected/actual verdicts, scores, reasons, evidence quotes, accumulated usage and the model identity are recorded in an immutable calibration report.

A report where every sample matches sets that grader version's `calibration_state` to `calibrated`; any mismatch sets `disagreement` with the offending samples listed. Editing a grader creates a new version and resets the state to `unverified` (the current silent carry-over is a defect this fixes). If the grader is edited while its calibration job runs, the finished report is saved marked stale and no state changes. Deterministic (non-judge) graders are rejected with an explicit message; a judge grader with no model and no explicit override is rejected too. Only one calibration job per grader may run at a time.

Calibration performs no target execution, touches no environments, confirms no project unknowns and never rewrites historical runs or their recorded judge results. Agreement on supplied samples is evidence about the grader, not proof of business truth; states and UI copy say so. The offline stub cannot calibrate (the real-model requirement is unchanged).

UI: grader cards show the live calibration state instead of a hardcoded 未校准; the grader detail view gains a calibration panel — sample editor, model selector, async job progress, the latest report with per-sample expected/actual comparison, and report history. No visual redesign beyond this panel.
